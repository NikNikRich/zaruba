# 08. Google Таблицы, публикация и режим показа

> Владелец правит Google Таблицу в браузере — Mini App обновляется сам: каждые
> 30 минут `pages-max.yml` скачивает листы, проверяет их и публикует Pages
> (§8.4). Выкладка на VPS стала ручной: `deploy.yml` запускается только кнопкой
> `Run workflow`, потому что основная публикация — бесплатная связка Pages +
> мини-ПК (`09-max-miniapp.md` §9.12).
>
> Связанные документы: `07-preview-data.md` — формат CSV и `data_tag`,
> `deploy/README.md` — ручной вариант выкладки (без Caddy, с nginx).

## 8.1. Книга для организаторов (10 минут)

Готовая книга — `docs/templates/ZARUBA_2026_MASTER.xlsx`. В ней одиннадцать
листов: первая вкладка «КАК ЗАПОЛНЯТЬ» объясняет правила обычными словами,
на рабочих листах русская шапка, вторая строка — подсказка «что писать»,
а там, где значений немного (тип данных, формат, `ДА`/`НЕТ`), стоит
выпадающий список. Книгу собирает скрипт из тех же CSV, что читает
`sync_tables`, поэтому шапка, подсказки и допустимые значения не расходятся
с моделью:

```powershell
.venv\Scripts\python.exe scripts\export_master_xlsx.py
```

| Шаг | Что сделать | Как проверить |
|---|---|---|
| 1. Загрузить книгу | Google Диск → «Создать → Загрузить файлы» → `ZARUBA_2026_MASTER.xlsx` | файл появился на Диске |
| 2. Открыть в Таблицах | правый клик → «Открыть с помощью → Google Таблицы», затем «Файл → Сохранить как таблицу Google» | в адресе есть `/spreadsheets/d/<SHEET_ID>` |
| 3. Проверить вкладки | «КАК ЗАПОЛНЯТЬ», «Расписание», «Номинации», «Судьи», «Студии», «Участники», «Выступления», «Оценки судей», «Оповещения», «Фото и видео», «Мерч и партнеры» | одиннадцать вкладок, на второй строке каждой — подсказка |
| 4. Открыть доступ | «Настройки доступа» → «Все, у кого есть ссылка» → «Читатель» | ссылка открывается в приватном окне без входа |
| 5. Взять `SHEET_ID` | из адреса `docs.google.com/spreadsheets/d/<SHEET_ID>/edit` | строка между `/d/` и `/edit` |
| 6. Взять `gid` листа | адрес с `#gid=<число>` — меняется при переключении листа | число для каждого листа из карты |
| 7. Собрать карту | JSON из шагов 5–6 в `ZARUBA_SHEETS_MAP` (§8.2) | `--from-sheets --check` пишет «ok» по каждому листу |

Заливать книгу в Google нужно один раз: дальше команда правит таблицу
в браузере, а GitHub Actions забирает листы по расписанию (§8.4).

### Из CSV по листам (если книги нет под рукой)

| Шаг | Что сделать | Как проверить |
|---|---|---|
| 1. Создать таблицу | `sheets.new` или «Google Диск → Создать → Таблица» | открылся пустой лист |
| 2. Загрузить лист | «Файл → Импорт → Загрузка» → `docs/templates/studios.csv`, разделитель «Точка с запятой», «Заменить данные текущего листа» | в первой строке шапка `slug, name, city, …` |
| 3. Добавить остальные | «+» внизу, имя листа = файл без `.csv` (`participants`, `blocks`, `performances`, `nominations`, `judges`, `media`, `commerce`), импорт так же | внизу восемь листов |
| 4. Открыть доступ | «Настройки доступа» → «Все, у кого есть ссылка» → «Читатель» | ссылка открывается в приватном окне без входа |
| 5. Взять `SHEET_ID` | из адреса `docs.google.com/spreadsheets/d/<SHEET_ID>/edit` | строка между `/d/` и `/edit` |
| 6. Взять `gid` листа | адрес с `#gid=<число>` — меняется при переключении листа | число для каждого из восьми листов |

Из шагов 5–6 собирается карта листов — одна строка JSON. Ключи ровно такие,
как `section` в `src/zaruba/sync_tables.py`:

```json
{"studios": "<gid>", "participants": "<gid>", "blocks": "<gid>", "performances": "<gid>", "nominations": "<gid>", "judges": "<gid>", "media": "<gid>", "commerce": "<gid>"}
```

Адреса экспорта скрипт собирает сам:
`https://docs.google.com/spreadsheets/d/<SHEET_ID>/export?format=csv&gid=<gid>`.
Вместо gid в карте допустим полный URL листа (например, ссылка «Опубликовать в
интернете» вида `…/pub?output=csv`). Если в карте нет хотя бы одного листа,
скрипт откажется работать: половина старых и половина новых данных — это не
«почти готово», а тихо испорченный каталог.

Проверить локально, ничего не записывая:

```powershell
$env:ZARUBA_SHEET_ID = "<SHEET_ID>"
$env:ZARUBA_SHEETS_MAP = '{"studios": "<gid>", "participants": "<gid>", "blocks": "<gid>", "performances": "<gid>", "nominations": "<gid>", "judges": "<gid>", "media": "<gid>", "commerce": "<gid>"}'
.venv\Scripts\python.exe -m zaruba.sync_tables --from-sheets --check
```

Лист `alerts` (срочные оповещения, `09-max-miniapp.md` §9.9) в карту добавляется
по желанию: `{"…": "…", "alerts": "<gid>"}`. Он не входит в overlay и не
обязателен — без него `content/alerts.yaml` остаётся пустым, а выгрузка таблиц
работает как раньше.

Лист `scores` («Оценки судей», `06-info-section.md` §6.28) — так же:
`{"…": "…", "scores": "<gid>"}`. Синоним ключа `results` принимается, чтобы
уже созданный секрет не пришлось переписывать. Без листа `content/scores.yaml`
не обновляется, и раздела «Оценки судей» на `/results` не появляется. Помните:
в файл и на страницу попадают только строки с `ДА` — черновики остаются
в таблице.

Без `--check` тот же запуск обновляет `docs/templates/*.csv` и overlay
`content/editions/2026.d/`. Без переменных окружения инструмент работает как
раньше — на локальных CSV.

| Что случилось | Что скажет скрипт |
|---|---|
| таблица закрыта | «вместо CSV пришёл HTML — таблица закрыта…» |
| сервер не ответил | «нет ответа за 10 с — лист не скачался» |
| неверный `gid` или `SHEET_ID` | «HTTP 404 — лист не найден: проверьте SHEET_ID и gid» |
| сломали шапку листа | «шапка не совпадает с моделью (нет [...], лишние [...])» |
| в карте не хватает листов | «не заданы листы [...]» |

При любой из этих ошибок локальные CSV и overlay остаются прежними: выгрузка
атомарна, запись начинается только после проверки всех листов.

## 8.2. Секреты GitHub

`Settings → Secrets and variables → Actions → New repository secret`.

| Секрет | Зачем | Где взять |
|---|---|---|
| `VPS_HOST` | адрес сервера для деплоя | IP или домен VPS |
| `VPS_USER` | пользователь SSH, под которым идёт деплой | `root` или пользователь из группы `docker` |
| `VPS_SSH_KEY` | приватный ключ деплоя | `ssh-keygen -t ed25519 -f deploy_key`; публичную часть — в `~/.ssh/authorized_keys` сервера |
| `SITE_HOST` | проверка живого сайта после выкладки; необязателен | домен |
| `VPS_KNOWN_HOSTS` | отпечаток хоста; необязателен | `ssh-keyscan -H <хост>` |
| `ZARUBA_SHEET_ID` | id таблицы (§8.1 п. 5) | адрес таблицы |
| `ZARUBA_SHEETS_MAP` | карта листов (§8.1) | одна строка JSON |

Два условия, без которых конвейеры молчат:

- `Settings → Actions → General → Workflow permissions` — «Read and write»:
  иначе `sync-sheets.yml` не сможет закоммитить обновлённые данные.
- Если `main` защищён, добавьте исключение для `zaruba-sync[bot]` или переведите
  синхронизацию на pull request: по умолчанию бот пушит прямо в `main`.

## 8.3. VPS за 5 минут

1. Создайте VPS (Ubuntu 24.04, 1 vCPU, 1 ГБ) и A-запись домена на его IP:
   `dig +short <домен>` должен вернуть этот IP. Пока записи нет, сертификат
   выпустить нельзя.
2. Войдите по SSH и выполните (если деплой пойдёт от `root`, `sudo` не нужен):

```bash
git clone <URL-репозитория> ~/zaruba-bootstrap && cd ~/zaruba-bootstrap
sudo bash deploy/setup_vps.sh                 # Docker, compose, ufw 22/80/443, /opt/zaruba

git clone <URL-репозитория> /opt/zaruba && cd /opt/zaruba
cp .env.example .env
nano .env        # ZARUBA_ENV=prod, DOMAIN=<домен>, ZARUBA_PUBLIC_BASE_URL=https://<домен>
chmod 600 .env

docker compose up -d --build
docker compose ps                             # web — healthy, caddy — running
SITE_HOST=<домен> bash deploy/smoke.sh        # все строки ok
```

3. Добавьте секреты из §8.2 и запустите деплой вручную: вкладка `Actions` →
   `deploy` → **Run workflow**. Автоматических прогонов у него больше нет
   (§8.4), поэтому шаг повторяется после каждого обновления на сервере.
   Проверка: запуск зелёный, сайт отвечает 200.

Caddy сам получает и продлевает сертификат Let's Encrypt: `certbot`, `cron` и
`nginx` для этой связки не нужны. `www.<домен>` подключается отдельно — блок в
`Caddyfile` закомментирован до появления A-записи на `www`.

## 8.4. Что происходит после правки таблицы

| Когда | Что | Сколько занимает |
|---|---|---|
| сразу | ничего: Pages собирается по расписанию | — |
| раз в 30 минут | `pages-max` скачивает листы, гоняет `content check` и `pytest`, собирает `dist/` и публикует Pages | 1–2 минуты |
| по кнопке | `sync-sheets` → **Run workflow**: те же листы, но с коммитом CSV и overlay в `main` | 1–2 минуты |
| по кнопке | `deploy` → **Run workflow**: проверки, `git reset --hard` в `/opt/zaruba`, `docker compose up -d --build`, `smoke.sh` | 2–3 минуты |

Итого задержка «правка → Pages» — до получаса плюс пара минут. Нужно быстрее:
вкладка `Actions` → `pages-max` → **Run workflow**. GitHub может задержать
запуск по расписанию в пиковые минуты — для контента, который заполняют руками,
это не критично.

Почему у `sync-sheets` и `deploy` нет ни расписания, ни пуша: без секретов
`VPS_*` автозапуск давал бы красный прогон на каждом коммите, а данные таблиц в
git нужны только тому, кто поднимает VPS заново. Постоянная публикация — это
`pages-max` и мини-ПК с ботом (`09-max-miniapp.md` §9.12).


## 8.5. Режим показа: `preview` и продакшн

| `ZARUBA_PREVIEW_ENABLED` | Что видит посетитель | Когда уместно |
|---|---|---|
| `1` | overlay подмешан: демонстрационные студии, участники, тайминг; баннер «предпросмотр», `noindex, nofollow` | пока реальных заявок нет, а вёрстку показать нужно |
| `0` (по умолчанию) | только подтверждённые факты из `content/editions/2026.yaml` | продакшн и старт продаж |

Снятие презентационных данных перед стартом продаж:

1. Строки таблиц, которые стали фактом, переведите на `data_tag: real` **и**
   внесите тот же факт в `content/editions/2026.yaml`: скрипт сверяет зеркало
   построчно и падает при расхождении. Строки, которых в выпуске нет, удалите.
2. `.venv\Scripts\python.exe -m zaruba.sync_tables --drop-preview` — overlay
   `content/editions/2026.d/` удаляется целиком.
3. `.venv\Scripts\python.exe -m zaruba.sync_tables --check` — проверка, что
   таблицы и overlay согласованы. Сразу после `--drop-preview` она сообщит, что
   файлов overlay нет: это ожидаемо, пока в таблицах не осталось `preview`-строк.
4. В `.env` на сервере: `ZARUBA_PREVIEW_ENABLED=0`, затем деплой.

Проверка результата: на `/` нет баннера «предпросмотр», в `<head>` нет
`noindex`, а `/performances` показывает либо реальные выступления, либо честное
пустое состояние.

## 8.6. Откат и аварии

| Ситуация | Что делать |
|---|---|
| данные таблицы сломали страницы | `git revert <коммит синхронизации>` и пуш: деплой вернёт прошлые данные |
| деплой не прошёл проверки | сайт остаётся на прежней версии: `deploy` не стартует, пока `check` красный |
| сервер не обновился | `cd /opt/zaruba && git reset --hard origin/main && docker compose up -d --build`, затем `smoke.sh` |
| потерян ключ деплоя | перевыпустить ключ, старый убрать из `authorized_keys`, обновить `VPS_SSH_KEY` |
| сгорел сервер | новый VPS по §8.3: состояние живёт в git, переносить нечего |
