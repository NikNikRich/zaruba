# 09. Mini App в MAX и бесплатный GitHub Pages

> Ответвление `feat/max-miniapp`: тот же сайт открывается внутри мессенджера
> MAX как мини-приложение. Инфраструктура — статика на GitHub Pages, 0 ₽.
> Спецификация MAX: <https://dev.max.ru/docs/webapps/introduction/> и
> <https://dev.max.ru/docs/webapps/bridge>.

## 9.1. Что меняет флаг `ZARUBA_MAX_MINIAPP=true`

| Что | Без флага | С флагом |
|---|---|---|
| MAX Bridge | не подключается | `https://st.max.ru/js/max-web-app.js` в конце `body`, затем `static/max-bridge.js` |
| CSP | `script-src 'self'`, `frame-ancestors 'none'` | `script-src 'self' https://st.max.ru`, `frame-ancestors 'self' https://max.ru https://*.max.ru` |
| `X-Frame-Options` | `DENY` | не отправляется: иначе десктопный клиент MAX не встроит страницу |
| Шапка | логотип «ЗАРУБА · Тюмень» и меню | логотип скрыт (нативный заголовок MAX уже называет бота), в меню добавлена «Главная» |
| Кнопка «Назад» | нет | `BackButton.hide()` на главной, `show()` на внутренних страницах, нажатие — `history.back()` |
| Внешние ссылки | обычный переход | `target="_blank"` перехватывается и открывается через `WebApp.openLink()` |

Вне MAX (`window.WebApp.platform === null`) адаптер не делает ничего: обычный
сайт остаётся обычным сайтом.

## 9.2. Локальная проверка

```powershell
$env:ZARUBA_MAX_MINIAPP = "true"
python -m uvicorn zaruba.main:app --port 8000
# в ответе: script-src ... https://st.max.ru, X-Frame-Options отсутствует,
# в шапке нет логотипа
```

Сборка ровно того, что уедет на Pages:

```powershell
$env:ZARUBA_ENV = "prod"
$env:ZARUBA_MAX_MINIAPP = "true"
python scripts/build_max_dist.py
python -m http.server 8001 --directory dist   # проверка относительных ссылок
```

Отдельно проверяется подпись `?startapp=`: открыть
`http://127.0.0.1:8001/?startapp=schedule` — адаптер перейдёт на
`schedule.html`, только если файл существует.

## 9.3. Включить GitHub Pages (5 шагов)

1. Ветка `feat/max-miniapp` запушена в GitHub; файл `.github/workflows/pages-max.yml` в ней есть.
2. Репозиторий → **Settings** → **Pages** → **Source**: выбрать **GitHub Actions**
   (не «Deploy from a branch»: тогда Pages возьмёт корень репозитория, а не `dist/`).
3. Репозиторий → **Actions** → workflow **pages-max** → **Run workflow**, ветка
   `feat/max-miniapp`. Пуш в эту ветку запускает его сам.
4. Дождаться зелёного job `deploy`; адрес будет в выводе job и в
   **Settings → Pages**: `https://<владелец>.github.io/<репозиторий>/`.
5. Открыть адрес в браузере: страницы и CSS должны работать без сервера.

Секреты `ZARUBA_SHEET_ID` и `ZARUBA_SHEETS_MAP` — те же, что у `sync-sheets.yml`
(`08-deploy-and-sheets.md`). Если `ZARUBA_SHEETS_MAP` не задан, сборка идёт на
данных репозитория и пишет `::notice::`, а не падает.

## 9.4. Ссылка на мини-приложение в MAX

1. Открыть <https://business.max.ru/self> → **Чат-боты** → **Перейти**.
2. Выбрать бота → **⋮** → **Настройки**.
3. Вставить адрес из шага 9.3 в поле URL мини-приложения.
4. Выбрать вид кнопки (**Открыть**, **Старт**, **Играть** или без названия) →
   **Сохранить**.

Требования MAX к адресу: только `https://`, не длиннее 1024 символов, латиница,
цифры, точка и дефис, без пробелов. Адрес `github.io` подходит; свой домен не
нужен. Если репозиторий переименован, адрес в настройках бота надо обновить —
иначе кнопка ведёт на 404.

## 9.5. Диплинки `?startapp=`

Формат: `https://max.ru/<bot>?startapp=<значение>`, значение — до 512 символов.
MAX передаёт его мини-приложению в `window.WebApp.initDataUnsafe.start_param`.
Адаптер понимает значение как путь страницы: `[a-z0-9]`, затем до 63 символов
`[a-z0-9/-]` — то есть и `schedule`, и вложенный `participants/ivan-petrov`;
переход только на существующий `<путь>.html` статической сборки.

| Диплинк | Куда попадёт пользователь |
|---|---|
| `https://max.ru/<bot>?startapp=schedule` | `schedule.html` — расписание |
| `https://max.ru/<bot>?startapp=participants` | `participants.html` — каталог участников |
| `https://max.ru/<bot>?startapp=participants/ivan-petrov` | карточка участника |
| `https://max.ru/<bot>?startapp=studios/pechat-tantsa` | карточка студии |
| `https://max.ru/<bot>?startapp=results` | `results.html` — результаты |
| `https://max.ru/<bot>` | главная, `start_param` пуст |

Доступные slug — это имена страниц из `scripts/build_static_preview.py`
(`SEED_PAGES`): `event`, `schedule`, `performances`, `participants`, `studios`,
`judges`, `results`, `tickets`, `venue`, `faq`, `media`, `privacy`, `about`,
`rules`, `takedown`, `glossary`, `history`, `ratings`, `search`.

Не передавайте в `startapp` конфиденциальные данные открытым текстом — только
одноразовые токены или идентификаторы сессии (требование MAX). Редирект
работает в статической сборке; на локальном FastAPI-стенде `<slug>.html` нет,
поэтому диплинк просто открывает главную.

## 9.6. Обновление и после слияния в `main`

- По расписанию (`*/30 * * * *`) и по пушу workflow забирает таблицы, гоняет
  `zaruba.content check`, `pytest`, собирает `dist/` и публикует Pages.
- GitHub запускает `schedule` только из workflow-файла в **ветке по умолчанию**.
  До слияния `pages-max.yml` в `main` расписание молчит: работают пуш в
  `feat/max-miniapp` и кнопка **Run workflow**.
- После слияния добавьте `main` в `on.push.branches`, чтобы Pages обновлялся и
  от коммитов в основную ветку.
- Коммитов workflow почти не делает: данные таблиц живут в опубликованном
  `dist/`, а не в истории. Исключение одно — лог срочных оповещений
  `content/editions/<год>.d/sent_alerts.json` (§9.9): без него следующий запуск
  разослал бы те же строки повторно.

## 9.7. Ограничения, о которых нужно помнить

- GitHub Pages отдаёт файлы как есть и **не присылает заголовки** из
  `middleware.py`: CSP и `X-Frame-Options` действуют только на FastAPI-стенде.
  Для Mini App это не проблема (страница и так внутри MAX), но проверять
  политику надо на `uvicorn`, а не на Pages.
- Копия на `github.io` закрыта от индексации файлом `robots.txt` с
  `Disallow: /`: `canonical` в статике срезается, а JSON-LD сохраняет адреса
  `testserver` — пусть робот лучше не видит эту копию вовсе.
- Поиск и фильтры — динамика FastAPI: в статике форма открывает каталог без
  параметров.
- Карточки участников, студий и выступлений в публичной сборке появляются
  только вместе с подтверждёнными данными: демо-строки из overlay
  `content/editions/2026.d/` включаются флагом `ZARUBA_PREVIEW_ENABLED=1` и на
  Pages намеренно выключены, поэтому каталоги показывают честные пустые
  состояния.
- `dist/` в `.gitignore`: публикуется артефакт сборки, а не папка в git.

## 9.8. Бот-проводник: «напиши слово — получи ссылку»

Бот живёт в том же приложении, что и сайт: MAX присылает событие на
`POST /max/webhook`, FastAPI отвечает `200` и уже после ответа отправляет
сообщение в чат через `platform-api2.max.ru/messages`. Отдельный контейнер,
база и очередь не нужны: ответ зависит только от текста события и настроек
(`src/zaruba/services/max_bot.py`).

| Событие | Ответ бота |
|---|---|
| `bot_started`, `/start`, `/start@<бот>`, «привет», «меню» | приветствие, кнопки «Открыть в MAX» и «Открыть сайт» |
| слово-раздел («расписание», «билеты», «как добраться») | название раздела и ссылка на его страницу |
| «билеты», «цена», «вход» | цена каждого билета по дням и действующий взнос участника |
| «расписание», «тайминг», «во сколько» | блоки по дням с временем; нет тайминга — так и написано |
| «где», «адрес», «площадка» | даты, адрес КТЗ «Золотые ворота Сибири», кнопка `/venue` |
| название студии или имя участника (от 4 символов) | сводка выступлений и кнопка на карточку |
| непонятный текст, пустое сообщение | список доступных разделов |
| сообщение от бота (`is_bot`), правки, удаления, `bot_stopped` | ответа нет |

### Ответы из живого контента

`plan_reply(update, settings, edition=…, venue=…, today=…)` получает тот же
`Edition`, что и страницы сайта (`load_latest`, кэш по отпечатку файлов), поэтому
бот не дублирует цифры, а берёт их из `content/editions/<год>.yaml`:

- **цена** — `tickets[].price` по дням; взнос участника считается по `early_until`
  и переданной дате `today`: до срока — ранняя ставка и её дедлайн, после —
  поздняя и дата, когда ранняя закончилась (`services/edition.fee_prices`);
- **блоки** — `blocks_for_day`, время `ЧЧ:ММ–ЧЧ:ММ` и название блока; у 2026
  тайминга в «Положении» нет, поэтому бот пишет «ещё не опубликован», а не
  выдумывает часы;
- **площадка** — даты и `Venue.address_line` из `content/venues.yaml`;
- **студия или участник** — поиск по имени без учёта кавычек и `ё` (совпадение
  ищется в обе стороны, короче 4 символов не ищем): ответ перечисляет до пяти
  выступлений с временем, номинацией и названием номера, а `open_app` ведёт на
  карточку `studios/<slug>` или `participants/<slug>` (§9.5).

Контент битый (`ContentError`) — webhook всё равно отвечает `200`, а бот
отвечает общей фразой со ссылкой: молчание хуже неточной формулировки, а 500
заставил бы MAX отписаться от бота.

Основа слова, а не целое: «расписание», «расписанию» и «расписании» ведут на
одну страницу. Проверяются по убыванию длины, поэтому «о сайте» — это раздел
«О сайте», а не «сайт» вообще.

| Слово | Раздел | Слово | Раздел |
|---|---|---|---|
| событ, номинац, возраст | `/event` | вопрос, faq | `/faq` |
| расписан, тайминг, блоки | `/schedule` | фото, видео, медиа | `/media` |
| выступлен | `/performances` | персональн, приват | `/privacy` |
| участник | `/participants` | о сайте, проект | `/about` |
| студи, школ | `/studios` | правил, положени | `/rules` |
| жюри, судь | `/judges` | удал, жалоб | `/takedown` |
| результат, победител | `/results` | глоссар, термин, направлен | `/glossary` |
| билет, вход, зрител | `/tickets` | истори, архив | `/history` |
| площадк, как добрат | `/venue` | рейтинг, балл | `/ratings` |

Кнопка `open_app` передаёт `slug` раздела мини-приложению — тот же параметр,
что понимает `?startapp=` (§9.5), поэтому человек попадает сразу на нужную
страницу. Кнопка `link` ведёт на саму страницу сайта. Нет `ZARUBA_MAX_BOT_NAME`
— остаётся только ссылка; нет адреса сайта — только текст.

| Переменная | Что это |
|---|---|
| `ZARUBA_MAX_BOT_TOKEN` | токен бота: «Чат-боты» → **⋮** → **Настройки** |
| `ZARUBA_MAX_BOT_SECRET` | секрет подписки, 5–256 символов `A–Z a–z 0–9 _ -` |
| `ZARUBA_MAX_BOT_NAME` | публичное имя бота для кнопки `open_app` |
| `ZARUBA_MAX_BOT_SITE_URL` | адрес сайта для ссылки; пусто — `ZARUBA_PUBLIC_BASE_URL` |
| `ZARUBA_MAX_BOT_CA_FILE` | PEM с корневым сертификатом Минцифры (см. ниже) |

Токен и секрет — это и есть включатель: без любого из них адрес `/max/webhook`
отвечает `404`, чтобы ненастроенный бот не висел открытым в интернете.

Порядок включения:

1. Задать переменные в `.env` на сервере и перезапустить `web`.
2. Подписать адрес на события (ключ — токен, URL — HTTPS на 443, без порта):

   ```bash
   curl -X POST "https://platform-api2.max.ru/subscriptions" \
     -H "Authorization: $ZARUBA_MAX_BOT_TOKEN" \
     -H "Content-Type: application/json" \
     -d '{"url":"https://<домен>/max/webhook","update_types":["message_created","bot_started"],"secret":"<секрет>"}'
   ```

3. Проверить, что адрес закрыт без секрета: `curl -s -o /dev/null -w '%{http_code}'
   -X POST https://<домен>/max/webhook` → `403`. Написать боту в MAX — ответ
   должен прийти в течение пары секунд.

Что важно помнить:

- **Ответ webhook — всегда `200`.** Любой другой код MAX считает сбоем доставки,
  повторяет запрос 10 раз и через 8 часов молчания отписывается сам. Поэтому
  мусор в теле — тоже `200`, а сбой отправки виден только в журнале `zaruba.max_bot`.
- **Секрет обязателен.** `X-Max-Bot-Api-Secret` — единственное доказательство,
  что запрос пришёл от MAX; сравнение идёт `secrets.compare_digest`.
- **Сертификат Минцифры.** Исходящие запросы к `platform-api2.max.ru` проверяют
  TLS как обычно: если в контейнере нет российского корневого сертификата,
  отправка падает с `SSL: CERTIFICATE_VERIFY_FAILED`. Лечится тем, что PEM
  кладётся в файл, а путь — в `ZARUBA_MAX_BOT_CA_FILE`; отключать проверку
  сертификата нельзя.
- **Состояния нет**, поэтому повторная доставка одного события даст второй
  ответ: дедупликация потребовала бы хранилища `mid`, а вред от дубля меньше
  цены базы в проводнике. Лимит MAX — 2 сообщения в секунду на диалог — при
  одном ответе на событие соблюдается.
- Бот отвечает ссылкой, но не отвечает вместо сайта: тексты, цифры и ответы
  организаторов остаются на страницах, где у каждого факта есть источник.

## 9.9. Срочные оповещения: лист `alerts` и рассылка в MAX

Оповещение — короткая строка «что изменилось» (перенос блока, отмена номинации,
вход с другого крыльца). Живёт она в отдельном листе `alerts` той же Google
Таблицы, а не в выпуске: плашка нужна на сутки, выпуск — на год.

Лист `alerts` (шапка ровно такая, порядок колонок значения не имеет):

| Колонка | Что это | Ограничения |
|---|---|---|
| `id` | ключ строки и ключ лога отправки | slug: латиница, цифры, дефис |
| `status` | `draft` — черновик, `send` — опубликовано | только эти два значения |
| `title` | заголовок плашки | 3–80 символов |
| `text` | само оповещение | 10–280 символов |
| `link_slug` | страница сайта для кнопки и ссылки | пусто или slug страницы |
| `urgent` | `true` — показать плашку на сайте | `true` / `false` |

Пустая таблица — законное состояние: «оповещений нет», а не ошибка. Строки
`send` без `urgent` уходят в MAX, но вёрстку не перекрашивают; `draft` не
уходит никуда. Файл `content/alerts.yaml` собирает синхронизация:

```powershell
python -m zaruba.sync_tables --from-sheets      # заодно пишет content/alerts.yaml
python -m zaruba.sync_tables --check --alerts-out content/alerts.yaml
```

`--check` сравнивает лист с файлом построчно и называет `id` и поле, которые
разошлись.

**Плашка на сайте.** Опубликованное срочное оповещение (`status=send`,
`urgent=true`) выводится яркой полосой в верхней части главной и расписания —
над шапкой, до контента. Вёрстка ничего не фильтрует: выбор строки делает
`services/alerts.active_alert` (первая подходящая строка в порядке таблицы,
поэтому новая строка ставится выше старой).

**Рассылка в MAX.**

```powershell
python -m zaruba.max_notify --send-alerts            # отправить очередь
python -m zaruba.max_notify --send-alerts --dry-run  # показать очередь, не отправляя
```

Команда берёт строки `status=send`, которых нет в
`content/editions/<год>.d/sent_alerts.json`, отправляет сообщение
`post_message()` в чат или канал `ZARUBA_MAX_ALERT_CHAT_ID` с кнопкой
`open_app` на `link_slug` и записывает `id` в лог **сразу после каждого
успешного сообщения**. Не доставлено — `id` в лог не попадает и строка
повторится при следующем запуске; код возврата при этом `1`.

| Переменная | Что это |
|---|---|
| `ZARUBA_MAX_ALERT_CHAT_ID` | числовой `chat_id` канала или чата для рассылки |
| `ZARUBA_MAX_BOT_TOKEN` | токен бота; не задан — команда пишет «рассылка пропущена» и выходит с `0` |

В `pages-max.yml` рассылка идёт после сборки статики, а лог коммитится тем же
job'ом (`contents: write`) с сообщением `[skip ci]`. Пуш из workflow через
`GITHUB_TOKEN` новых запусков не вызывает, поэтому цикла нет. Сбой доставки
помечен `continue-on-error`: страницы публикуются в любом случае.

**Как разослать прямо сейчас:** правка таблицы → **Actions → pages-max → Run
workflow**. Обычный путь — расписание `*/30`: тот же прогон и обновляет
страницы, и рассылает новые строки.

**Почему лог, а не `sent_at` в таблице:** запись обратно в чужую Google Таблицу
требует права записи у CI. Лог в репозитории дешевле и виден в истории git.
Ограничение честное: два прогона одновременно (ручной и плановый) могут успеть
отправить одну строку дважды — параллельные запуски `pages-max` разводит
`concurrency: pages-max`.

## 9.10. Бот без VPS: long polling

Вебхук требует домена с HTTPS и белого IP. Mini App живёт на бесплатном GitHub
Pages, поэтому основной режим бота — **long polling**: бот сам спрашивает MAX
`GET /updates`, сервер держит запрос до 30 секунд и отвечает сразу, как только
событие появилось. Ни адреса, ни сертификата на входе не нужно.

```powershell
python -m zaruba.max_bot --once        # один запрос: проверка токена и TLS
python -m zaruba.max_bot --polling     # цикл до Ctrl+C
python -m zaruba.max_bot --polling --timeout 30 --pause 1
```

- Работает с любого ПК в день чемпионата: достаточно `ZARUBA_MAX_BOT_TOKEN` и
  (при необходимости) `ZARUBA_MAX_BOT_CA_FILE`. Запуск без токена — код `1` и
  объяснение; путь к несуществующему сертификату проверяется до сети.
- Ответы те же, что у вебхука: `poll_once` собирает пачку событий, читает
  `Edition` один раз и отправляет ответы через тот же `post_message`.
- Сеть отвалилась — пустой ответ и следующий запрос с тем же `marker`: цикл
  переживает ночной обрыв. `marker` живёт в памяти процесса: без него MAX
  отдаёт только последнее событие, поэтому после перезапуска возможен один
  повторный ответ. Хранилище ради этого не заводим.
- Вебхук `/max/webhook` остаётся рабочим: переезд на VPS — это `POST
  /subscriptions` и переменные окружения, а не правка кода (§9.8).
- Long polling и вебхук одновременно держать не нужно: MAX доставит событие
  тому каналу, который подписан. При живом вебхуке опрос просто не нужен.

Ограничение: бесплатный воркер CI для этого не годится — job GitHub Actions
живёт минуты, а бот нужен часами. Подойдёт любой ПК с Python и интернетом.
